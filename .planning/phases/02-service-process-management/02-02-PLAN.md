GameProcessPriorityTweak (PROC-01):
- Description: Sets the active game process to High priority for improved performance
- Uses ProcessNames = [] (empty — process is selected at runtime by the user)
- ProcessPriority = "High"
- The executor needs a way to know which process to target — extend the ApplyAsync to accept a process name parameter or use a runtime-resolved process

Implementation: GameProcessPriorityTweak provides the definition with ProcessPriority="High". The ProcessOperationExecutor.ApplyAsync checks if the definition has ProcessNames — if so, kills them (PROC-02). If the definition has ProcessPriority set, it needs a target process name — this is passed at call time. The TweakEngine.ApplyAsync already takes a tweakId, so the process name needs to come from somewhere.

Resolution: Add an optional `targetProcessName` parameter to ITweakExecutor.ApplyAsync. But this changes the interface signature used by all executors. Instead, add a new method to ProcessOperationExecutor specifically: `ApplyWithTargetAsync(TweakDefinition definition, string processName)`. The TweakEngine doesn't need to change — the UI (Phase 4) will call the executor directly for process priority, or the definition can carry a default process name pattern.

Actually, following the existing pattern more closely: The GameProcessPriorityTweak Definition has ProcessPriority="High" and no fixed ProcessNames (since the game varies). The executor's ApplyAsync uses definition.ProcessNames if populated. For PROC-01, the UI will resolve the target process at runtime and call ApplyAsync with a definition that has the process name injected. For unit testing, we test the executor with a definition that has ProcessNames populated.

For the test: Create a test definition with ProcessNames=["game.exe"], ProcessPriority="High", verify executor.SetPriorityAsync called. For BackgroundProcessesTweak, verify KillAsync called with the full kill list.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Process kill vs Process priority | Kill is destructive (requires user confirmation in UI), priority is reversible |
| Runtime process selection | GameProcessPriorityTweak needs process name resolved at runtime — injection happens via UI, not from untrusted data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | Process name list | medium | mitigate | Process names are hardcoded in tweak classes (trusted source from Priority.ps1); not user-controllable |
| T-05-02 | Repudiation | Process kill without logging | high | mitigate | All process operations logged via ILogService with process name, operation, and outcome |
| T-05-03 | Spoofing | ProcessPriorityClass values | low | mitigate | Enum-based priority (RealTime, High, AboveNormal, etc.) — no string parsing of untrusted input |
| T-05-SC | Availability | Process kill affecting critical system | high | mitigate | Kill list is curated from Priority.ps1 — game launchers only, never system processes |

## Notes
- ProcessNotFoundException is expected during kill (processes may have already exited) — handle gracefully with logging
- System.Diagnostics.Process is part of .NET 10 runtime (no NuGet needed)
</threat_model>
